02 / THE IDEA

Don't take the AI's word. Make it show proof.

Same change, two reviews. One gives an opinion. The other runs a test that anyone can repeat.

A normal AI review

“The code runs, and every test passes. ✓ Approve.”
What it missed: the tests never tried exactly one condition being true.
Sounds sure. Shows nothing you can check.

Our review

  1. 1
    Write down the ruleRecent OR defective must qualify.
  2. 2
    Try the missing caserefund_ok(False, True)
  3. 3
    Compare the answersExpected True, got False → REFUTED.
Anyone can run that case and see the mismatch.
An opinion can be wrong without anyone noticing. A test shows you.15 s

03 / STEP 1 · GATHER EVIDENCE

Step 1: gather the evidence.

What was promised, what changed, and what the agent said, if its session was saved. Then put them side by side.

MongoDB stores the links. Missing Entire session? Intent stays unknown.12 s

04 / STEP 2 · MAKE IT CHECKABLE

Step 2: state the rule precisely.

Two yes/no conditions give four possible cases. The function must return the same answer as the policy for every one.

Every claim keeps a link to where it came from - that is the audit trail.11 s

05 / STEP 3 · CHECK ALL FOUR CASES

Two missing cases reveal the mistake.

The existing tests covered the ends. We check every combination and compare the policy with the code.

The four-case domain is complete; downstream impact remains unconfirmed until tested.13 s

06 / STEP 4 · ANSWER HONESTLY

Step 4: only four honest answers.

An answer only counts if a real run produced it. The AI can suggest ideas, but it can't hand out answers.

No “looks good to me” - those four words are the whole vocabulary.11 s

07 / HOW IT GROWS

We check promises, not lines.

One promise covers many lines. Each review only reads what changed - and every promise already checked becomes a test for the next change.

Today each review lists the earlier promises it re-checks; an automatic shared registry is the next step.13 s
